# تشخيص فحص Sitemap ونسخ PHP — 2026-10-21

## الخلاصة

كان فاحص SEO يرفض XML صالحاً عند وجود تعليمة XSL قبل جذر sitemap، وهي موجودة في ملفات sitemap الفرعية التي تنتجها الحزمة الحالية. عُدّل محلل الجذر ليتجاوز تعليمات XML المعالجة والتعليقات الصحيحة قبل الجذر، وأضيفت اختبارات لملف `urlset` المباشر، وفهرس `sitemapindex`، والملفات الفرعية المزينة بـXSL وروابط `xhtml:link`.

تحذير المتصفح عن تقادم `XSLTProcessor` لا يسبب هذا الفشل؛ إنه متعلق بعرض نسخة XSL المرئية في المتصفح، لا بصحة XML الذي يقرأه الفاحص.

## مقارنة ملفات PHP المرفقة

- `index_(2)` و`index_(3)` متطابقان بايتاً، وكلاهما يطابق `build_php/api/index.php` الحالي.
- نسخة `aiservx` أقدم: تثبت `CANONICAL_SITE_URL` على `https://aiservx.com` ولا تستخدم تقسيم sitemap أو مساعد أصل التشغيل.
- نسخة `alsahmm` أقدم أيضاً وتثبت الأصل على `https://alsahmm.com`، ولا تستخدم التقسيم.
- النسخة الحالية تستنتج الأصل من المضيف والبروتوكول الواردين، وتعيد خريطة sitemap على شكل فهرس عندما تتجاوز عدد العناوين الحد لكل ملف.

لذلك فالاختلاف بين الملفات اختلاف إصدارات وسلوك، وليس قاعدة تجعل كل ملف صالحاً لدومين معين. في اختبار PHP محلي مع قاعدة بيانات منسوخة، رجعت `settings` و`packages` و`/sitemap/generate` بحالة 200 في النسختين القديمتين والجديدة. النسختان القديمتان أعادتا أصل الدومين المثبت داخل الملف؛ أما النسخة الجديدة فأعادت أصل المضيف التجريبي لكل من `aiservx.example` و`alsahmm.example`. وأعادت النسخة الجديدة فهرساً يحوي 508 عنواناً وملفي sitemap فرعيين.

## أخطاء 500 في API

نسخة API الحالية تستدعي ملفات PHP مساعدة من مجلد `api/` قبل تشغيل أي مسار. حزمة التحديث تضم تسعة ملفات PHP وJSON مساعدة إلى جانب `index.php`. تجربة ملف `index.php` وحده، من دون ملفاته المساعدة، أعادت HTTP 500 لكل من `settings` و`packages`، ما يطابق نمط العطل الشامل الظاهر في سجل المتصفح.

لكن لم يمكن إثبات أن هذا هو سبب أخطاء الإنتاج السابقة من السجل وحده. في فحص `https://aiservx.com` بتاريخ 2026-10-21 أعادت `settings` و`packages` HTTP 200؛ وأعادت المسارات المحمية `auth/me` و`admin/sidebar-counts` HTTP 401 بلا جلسة، وهو متوقع. إذا عاد 500 بعد الرفع، تحقق من وجود جميع ملفات `api/` المساعدة في جذر النطاق الفعلي، ثم راجع سجل أخطاء PHP وصلاحيات/وجود قاعدة SQLite. صفحة الإعدادات وحدها لا تكفي لتحديد أي من هذه الأسباب.

## التحقق المنفذ

- اجتاز كل ملف PHP مرفق فحص `php -l`.
- نجح اختبار عقد حزمة API، وتأكد وجود الملفات المساعدة التسعة.
- نجح اختبار sitemap runtime للحزمة واختبار فاحص SEO بعد إضافة تعليمات XSL وروابط `xhtml:link`.
- تحقق محلل الواجهة من ملف sitemap الحي لـ`aiservx.com` ومن الفهرس والملفين الفرعيين الفعليين في الحزمة الحالية.
- شُغلت ثلاثة إصدارات مميزة من ملفات PHP محلياً على نسخ منفصلة من قاعدة البيانات؛ لم تُعدّل قاعدة إنتاجية ولم يُرفع شيء إلى Hostinger.

## ما لم يتم التحقق منه

الاختبارات أعلاه محلية ومحاكاة بمضيفي HTTPS، ولا تثبت الملفات الموجودة حالياً في Document Root الفعلي على كل نطاق Hostinger. كما أن استجابة aiservx الحية وقت الفحص لا تنفي أن 500 ظهر قبل ذلك أو على نطاق آخر. يلزم بعد رفع مجلد API كاملاً فحص `settings` و`packages` و`sitemap.xml` والملفات الفرعية على كل نطاق متأثر، ثم مطابقة النتيجة مع سجل أخطاء PHP.

## تحديث الاستكمال — 2026-10-22

### نتيجة فحص sitemap المنشور

- أعاد `https://alsahmm.com/sitemap.xml` حالة HTTP 200 ونوع المحتوى `application/xml`.
- اجتاز الملف الكامل تحليل XML؛ جذر المستند `urlset` ويضم 502 رابطاً، وجميع الروابط المقروءة تستخدم المضيف `alsahmm.com`.
- لم يظهر الرمز `__CLEANFLOW_SITE_ORIGIN__` في الاستجابة الحية، وكان وسم `</urlset>` موجوداً.
- هذا يثبت صلاحية استجابة sitemap العامة وقت الفحص فقط؛ لا يثبت أن حزمة API الجديدة رُفعت أو أن مسارات API تعمل على Hostinger.

### حزمة API الجديدة

- أُعيد إنشاء `generated-artifacts/updates/cleanflow-hostinger-api-update.zip` بحيث يطابق `api/index.php` الملف PHP المرفق و`build_php/api/index.php` بايتاً ببايت، مع ملفات التشغيل المساعدة التسعة الحالية.
- يحتوي الأرشيف على 13 مدخلاً: `api/index.php` و`.htaccess` وتسعة ملفات PHP/JSON مساعدة، إضافة إلى `UPLOAD_INSTRUCTIONS.txt`.
- طابقت ملفات التشغيل التسعة مصادرها الحالية، واجتازت ملفات PHP في الحزمة `php -l`، ونجح اختبار عقد الحزمة واختبار sitemap runtime.
- تؤكد هذه النتائج سلامة الحزمة محلياً فقط، ولا تضمن وحدها حل خطأ 500 على مضيف الإنتاج.

### دليل خطأ 500 بعد الرفع

- أظهر سجل المتصفح المرفق حالات 500 لمسارات `/api/settings` و`/api/packages` و`/api/auth/login`، مع ترويسة `PHP/7.4.33`. تحذير `xslt-polyfill` ورسالة `Target website not loaded` منفصلان عن استجابة API ولا يحددان سبب 500.
- ملف PHP المرفق يطابق نسخة البناء المحلية `build_php/api/index.php` بايتاً ببايت. وتختلف هذه النسخة عن قالب `scripts/api-index.php` الحالي في بعض التغييرات الأحدث؛ لذلك لا يجوز افتراض أن استبدال الملف وحده عالج السبب اعتماداً على اللقطات فقط.
- توقيتا الترويسة المرسلان متعارضان مع ترتيب وصف المستخدم: استجابة 200 مؤرخة 08:45:49، واستجابة 500 مؤرخة 08:47:21، كما تختلف عقدة HCDN بينهما. لا تثبت هذه اللقطات أن استجابة 200 جاءت بعد الاستبدال.
- بعد ذلك أكد المستخدم أنه غيّر إصدار PHP على Hostinger من 7.4 إلى 8.5، وأن API أصبح يعمل مع ملف `index.php` الأصلي ومع الملف المرسل. وفق تحقق المستخدم، كان اختلاف إصدار PHP سبب المشكلة؛ لا يتطلب هذا الإصلاح استبدال index.php.
- لا توجد قراءة مستقلة لسجل PHP، لذلك مصدر عدم التوافق التفصيلي غير معروف. لكن نتيجة المستخدم الحية بعد تغيير إصدار PHP تؤكد زوال 500.

### تحليل أرشيف Sitemap المرفق — 2026-10-22

- الأرشيف يحوي ثلاثة ملفات: `sitemap.xml` فهرس `sitemapindex` صحيح يشير إلى ملفين فرعيين، و`sitemap1.xml` يحوي 500 رابط، و`sitemap2.xml` يحوي 8 روابط. مجموع 508 روابط فريدة بلا تكرار؛ التقسيم عند 500 رابط هو السلوك المتوقع للإعداد الحالي.
- ملفات XML داخل الأرشيف الخام تحتوي الرمز `__CLEANFLOW_SITE_ORIGIN__`. هذا مقصود لملفات التخزين: يجب أن تمر الاستجابة العامة عبر `site-response.php` كي يستبدل الرمز بأصل الموقع. لا تستخدم ملفات التخزين الخام كما هي في Search Console.
- بعد تغيير PHP، جرى فحص الروابط العامة الثلاثة مباشرة: جميعها أعادت HTTP 200 و`application/xml`، والفهرس أشار إلى `https://alsahmm.com/sitemap1.xml` و`https://alsahmm.com/sitemap2.xml`. احتوت الملفات الفرعية الـ508 رابطاً مطلقاً على `alsahmm.com`، دون رموز أصل أو روابط مكررة.
- لذلك ملفات sitemap الثلاثة صحيحة على الموقع الحي وقت الفحص. إذا كان المطلوب ملفاً واحداً بدلاً من التقسيم، غيّر إعداد تقسيم sitemap؛ لا حاجة لإصلاح استبدال الأصل أو تعديل ملفات XML يدوياً.

### الحالة الحالية

- المستخدم أكد أن API عاد للعمل بعد تغيير PHP إلى 8.5، مع أي من ملفي index.
- sitemap العام صالح ومقسّم إلى فهرس وملفين فرعيين. لم تُعدّل الملفات الحية أو إعداد التقسيم خلال هذا الفحص.
