# سجل تنفيذ بوابة Rank Math وبناء الحزم

هذا الملف يسجل نطاق العمل والحقائق والقرارات التنفيذية القابلة للمراجعة. لا يُعد تقرير نشر أو دليلاً على نجاح الحزم قبل اكتمال التحقق.

## قاعدة ثبات الروابط — ملزمة لكل تعديل

- لا تغيّر رابط أي صفحة تجتاز البناء؛ روابطها الحالية مفهرسة ويجب أن تبقى كما هي.
- لا يُسمح بتغيير رابط إلا لصفحة تفشل في البناء، وفقط عندما يكون الرابط نفسه جزءاً من سبب الفشل ولا يمكن إصلاح الدرجة دون تغييره.
- إنشاء رابط جديد مسموح عند الحاجة إلى مسار غير موجود؛ تعديل أو إنشاء الروابط إجراء نادر.
- إذا اضطررنا إلى تغيير رابط صفحة فاشلة، احتفظ بالرابط القديم بتحويل دائم، وحدّث الروابط الداخلية وcanonical ونسختي sitemap.

## المطلوب

- تشغيل محلل Rank Math المشترك على كل صفحة HTML مولّدة، بما فيها صفحات sitemap والصفحات الإضافية مثل `/call-now`.
- إظهار رابط الصفحة والاختبارات التي منعتها من بلوغ 100/100، وإيقاف إنشاء الحزمة عند أي نتيجة أقل من 100.
- تطبيق الفحص نفسه على حزمتي Hostinger PHP وNode.
- بناء الحزم بعد تطبيق البوابة والتحقق من النتيجة.

## ما تم التحقق منه

- البوابة السابقة تفحص sitemap ووجود HTML وcanonical، لكنها لا تشغّل `analyzeRankMathSeo`.
- مجلد الواجهة الثابتة الحالي يحتوي 488 ملف HTML؛ مجلدا PHP وNode يحتوي كل منهما 489 ملفاً، ويتضمنان صفحة CleanFlow Platform الإضافية.
- الحزمتان الموجودتان قديمتان (من 18 أكتوبر 2026)، ولا تمثلان بناء هذه المهمة.
- محلل المشروع متاح من `@workspace/seo-rank-math`، ويحتوي محولات بيانات المقالات وصفحات SEO ومحتوى الخدمات والباقات.
- بعض الصفحات الثابتة لا تحمل عبارة تركيز، بينما صفحاتها تمرر قائمة كلمات مفتاحية إلى مولد HTML.
- بناء Hostinger يتضمن خطوة مركزية سبق تطبيقها على قاعدة التطوير؛ سجلات التحويل المعروفة كانت غير نشطة عند الفحص.

## قرارات التنفيذ

- تشغيل بوابة البناء عبر `tsx` لتحميل المحلل المشترك المكتوب بـTypeScript من أداة الفحص.
- استخدام سجلات قاعدة بيانات كل حزمة للمحتوى الذي يملكه المحرر، واستخدام HTML النهائي للبيانات الخاصة بالصفحات الثابتة والمناطق.
- عدم اشتقاق عبارة التركيز بصمت عند غيابها؛ يجب أن يكون مصدرها محفوظاً أو محدداً صراحةً في إعداد الصفحة.
- حفظ جرد روابط الصفحات قبل الإصلاح؛ صفحات النجاح لا تُمس، والصفحات الفاشلة لا يتغير رابطها إلا عند ثبوت أن ذلك شرط لاجتياز البوابة.
- فحص صفحات PHP وNode قبل إنشاء أرشيف جديد، ومقارنة ملفات HTML المعبأة بين الحزمتين.

## التقدم الحالي

- تم تحويل أمر `seo:gate` لاستخدام `tsx`.
- تم ربط بوابة الفحص بالمحلل المشترك ومحوّلات المقالات وصفحات SEO ومحتوى الخدمات والباقات.
- تتطلب المحوّلات حقول JavaScript camelCase؛ مررتُ إليها تحويلات صريحة من أعمدة SQLite snake_case بعد أن كشف تقرير التفاصيل أن الربط السابق أعطى قراءة ناقصة للبيانات المحفوظة.
- تم تعديل مولد الصفحات الثابتة لاستخدام أول كلمة مفتاحية صريحة كعبارة تركيز عندما لا يمرر المستدعي عبارة منفصلة.
- أُصلح تطبيع المسار في جرد HTML بعد اختبار كشف إنشاء عنوان متوقع ببداية مزدوجة؛ أعيد تشغيل الفحص بعد الإصلاح.
- نتيجة الفحص الأولى قبل إصلاح ربط الحقول كانت 2/489، ثم أُعيد الفحص بعد التصحيح: 205/489 اجتازت 100/100 و284 فقط لم تجتز. الصفحات الـ205 الناجحة مستثناة من أي تغيير في روابطها ومحتواها.
- تشمل أسباب الفشل المتبقية أطوال الأوصاف، عمق بعض المقالات والصفحات، وتطابق عبارة التركيز مع الوصف أو H1 أو المقدمة أو المسار. صفحة التطبيق الإضافية `/cleanflow-platform` تحتاج أيضاً مراجعة HTML مستقلة. لم تُخفّف قواعد المحلل أو شرط 100/100.
- أوقف الفحص بناء الحزم قبل إنشاء أرشيف جديد؛ بقي أرشيف PHP (60,751,865 بايت) وأرشيف Node (63,389,556 بايت) بتاريخ 18 أكتوبر 2026 دون استبدال.
- تم جعل إنشاء الأرشيفين مرحلياً: يُفحص الملف المرشح قبل اعتماده، ويُنشأ أرشيف PHP بعد اجتياز فحص PHP وNode ومقارنة HTML بينهما.
- نجحت اختبارات صياغة JavaScript وفحص TypeScript لحزمة scripts. البناء الكامل لم يكتمل؛ الأرشيفان الموجودان لا يتضمنان هذه التغييرات.

## سجل النتائج

النتيجة في نهاية مرحلة بوابة البناء: البوابة تمنع الشحن كما ينبغي، لكن المحتوى لا يحقق حد 100/100؛ لذلك لم تُنتج حزم جديدة. يتطلب إصدار حزم جديدة مراجعة أسباب الفشل وإصلاحها. تبقى روابط الصفحات الناجحة دون تغيير، ولا يتغير رابط صفحة فاشلة إلا إذا ثبت أن الرابط نفسه سبب ضروري للإخفاق؛ إنشاء الروابط الجديدة نادر ومسموح للحاجة غير المغطاة.

## استكمال تدقيق الإنتاج والتقرير التشغيلي — 19 أكتوبر 2026

### ما أُنجز

- لوحة تدقيق SEO الحالية تتيح بناء sitemap وحفظه على الخادم، ثم تشغيل التدقيق مباشرة بعد نجاح الحفظ. انخفاض درجات الصفحات لا يوقف الفحص؛ أخطاء sitemap أو تعذر جلب مصدر التدقيق تظل أخطاء تشغيلية تمنع نتيجة غير موثوقة.
- التدقيق يجمع روابط sitemap مع جرد ملفات HTML المنشورة، ويضيف الصفحات الموجودة في الملفات وغير الموجودة في الخريطة إلى التقرير. تحفظ النتيجة الأخيرة على الخادم وتظهر عند العودة إلى اللوحة، مع الإبقاء على سلوك النسخة المحلية الاحتياطية.
- API الخاصة بـNode تحتوي مسار جرد HTML محمياً بصلاحية SEO. أُضيف المسار المكافئ إلى API الخاصة باستضافة PHP المشتركة؛ يمسح جذر الموقع المنشور دون اتباع الروابط الرمزية، ويعيد المسارات فقط، مع حد أمان قدره 20,000 ملف.
- يعرض التقرير الصفحة ودرجة المحلل والفحوص المتعثرة ونوع كل فحص. روابط المحرر والإصلاح الآلي متاحة للسجلات التي لها محرر CMS؛ أُضيف دعم فتح محرر الباقات وتمرير إصلاح الباقة إلى مسار الحفظ، مع تحليل المحتوى المرئي المركّب للباقة قبل قبول الإصلاح. صفحات القوالب الثابتة والمناطق لا تملك بعد محرراً داخلياً أو مسار إصلاح آلياً.

### التحقق والقيود الحالية

- نجح `pnpm run typecheck` لكامل مساحة العمل، ونجح `php -l scripts/api-index.php`. نجحت أيضاً اختبارات `test:rank-math-fix-targets` و`test:rank-math-input-parity` و`test:seo-audit-urls` و`test:seo-audit-storage` و`test:hostinger-seo-fix-retry`.
- بعد إعادة تشغيل API وواجهة الموقع، أعاد فحص الصحة HTTP 200؛ وأعاد مسار جرد HTML على Node HTTP 401 دون تسجيل دخول، بما يؤكد أن المسار موجود ولا يسمح بالوصول المجهول. هذا لا يحل محل اختبار PHP على Hostinger.
- أعيد تشغيل بوابة Rank Math على مخرجات PHP وNode الموجودة: 489 صفحة في كل حزمة، اجتازت 205 صفحات فقط من كل مجموعة 100/100، وبقيت 284 صفحة فاشلة لكل حزمة.
- تحليل نسخة PHP من الإخفاقات الـ284 يوزعها إلى: 158 صفحة SEO، 50 صفحة حي، 33 مقالاً، 16 خدمة، 16 باقة، و11 صفحة ثابتة. قاعدة بيانات المصدر `data/sabaik.db` وقاعدتا PHP وNode المرحليتان متطابقة في جداول SEO والإعدادات المفحوصة؛ لذلك تبدأ المعالجة من المصدر نفسه، لا من نسخ قاعدة مختلفة.
- في نسخة PHP وحدها، أكثر الفحوص الفاشلة تكراراً: طول الوصف 173، المقدمة 144، عبارة التركيز في الوصف 123 وH1 120، مسار الرابط 119، وعمق المحتوى 54. هذه أعداد فحوص، وقد يجتمع أكثر من فحص على الصفحة نفسها.
- فحص عبارة التركيز في المسار هو عائق خاص في 119 صفحة: 50 منطقة، 32 مقالة، 16 باقة، 11 خدمة، و10 صفحات ثابتة. كثير من المسارات لاتينية بينما عبارة التركيز عربية. لا يُصلح هذا بحشو كلمات أو تغيير عبارة التركيز إلى ترجمة غير طبيعية؛ يجب اختبار التطابق الصوتي/التهجئة اللاتينية الطبيعية أولاً. إذا بقي شرط 100/100 متوقفاً على المسار، يتطلب ذلك تحويلاً 301 وتحديث الروابط الداخلية وcanonical وsitemap، ويجب حصره في الصفحات الفاشلة.
- تتضمن مجموعة الصفحات الثابتة `/cleanflow-platform`، وبوابتها مختلفة عن صفحات خدمات التنظيف: عبارة تركيز وH1 ومحتوى وcanonical وروابط داخلية وبيانات منظمة. يلزم تحديد هدفها التحريري قبل صياغة محتواها، لا نسخ قالب صفحات التنظيف إليها.
- سكربت `scripts/complete-seo-content-and-metadata.mjs` غير مناسب للتشغيل كما هو لهذه المعالجة المحدودة: يعيد تطبيع كلمات/وسوم في مجموعات كاملة من الجداول، وليس الصفحات الفاشلة وحدها. لا يُشغّل على قاعدة المصدر في هذه المهمة دون حصر التغييرات وتدقيق الصفوف قبل الحفظ.
- كشف الفحص أيضاً اختلافاً بايتياً في 99 ملف HTML بين مجلدي PHP وNode المرحليين الموجودين حالياً. ملفات ZIP أقدم من مخرجات البناء المرحلية؛ لذلك لا يثبت هذا وحده اختلاف المولّدات، ويجب إعادة المقارنة بعد بناء مرشحين جديدين من مصدر واحد.
- الحزم المنشورة في مجلد المخرجات ما زالت بتاريخ 18 أكتوبر 2026، ولا تحتوي تنفيذات هذه المرحلة. لم تُستبدل الأرشيفات ولم يُعلن نجاح حزمة جديدة: بوابة 100/100 ما زالت تمنع الإصدار.
- تنفيذ API الإنتاجية يختلف حسب نوع الاستضافة: PHP هو المسار الفعلي للاستضافة المشتركة، وNode مسار مستقل؛ لذلك لا يكفي نجاح أحدهما أو نجاح المعاينة المحلية. لم يُتحقق من المسارات على موقع Hostinger الحي في هذه المرحلة.

### حدود الإصلاح قبل إصدار حزمة

- الحفاظ على عناوين الصفحات الناجحة ومحتواها كما هو. لا يعالج إخفاق الكلمة في المسار بتغيير URL تلقائياً؛ يلزم إثبات أن المسار نفسه هو العائق وعدم كفاية إصلاح العنوان أو الوصف أو المحتوى.
- وافق المستخدم على إصلاح الصفحات الفاشلة فقط. لا تلمس الصفحات الـ205 المجتازة أو روابطها، واحفظ نسخة استرجاع متسقة قبل تحديث بيانات المصدر. اجعل التغييرات صريحة ومقصورة على الحقول التي يثبت التقرير حاجتها للإصلاح، ثم أعد الفحص بالمحلل نفسه.
- موافقة إصلاح المحتوى لا تعني تغيير المسارات تلقائياً. لا تغيّر URL إلا إذا ظل اختبار المسار هو سبب عدم بلوغ 100/100 بعد تجربة تطابق صوتي طبيعي؛ وإذا لزم تغيير حقيقي، حافظ على المسار القديم بتحويل دائم وحدّث الروابط الداخلية وcanonical وsitemap قبل إعادة الفحص.
- لا تُبنى حزم Hostinger النهائية حتى تجتاز كل صفحة HTML البوابة في PHP وNode وتُقارن مجموعتا الملفات وHTML وsitemap. يلزم بعد الرفع فحص sitemap والاستجابات الحية مباشرة.

## متابعة تحليل تطابق الكلمات المفتاحية مع المسارات — 19 أكتوبر 2026

### إعادة تحقق للمدخلات

- أُعيد تشغيل تقرير Rank Math للقراءة فقط على ملفات HTML وقاعدة SQLite المرحلية لحزمة PHP، وحُفظ التقرير المؤقت خارج المشروع. النتيجة أعادت تأكيد الأرقام السابقة: 489 صفحة، 205 صفحات بدرجة 100/100، و284 صفحة دونها.
- وُجد تحذير `keyword-url` في 119 صفحة: 50 منطقة، و32 مقالاً، و16 باقة، و11 خدمة، و10 صفحات ثابتة. بقيت أعداد بقية الفحوص كما في التقرير السابق؛ هذا تحذير على مستوى الفحص وليس سبباً وحيداً للإخفاق في أغلب هذه الصفحات.
- أمثلة المناطق توضح حالة تطابق صوتي مقصود: `/areas/al-aarid` مقابل «شركة تنظيف حي العارض بالرياض»، وكذلك `/areas/north-riyadh` مقابل «شركة تنظيف شمال الرياض». المسار يحمل اسم الحي/الجهة باللاتينية ولا يحمل العبارة العربية الكاملة.
- الصفحات الثابتة مثل `/terms` و`/about` تستخدم مسارات إنجليزية مألوفة يقابلها معنى عربي في العبارة المستهدفة. أما بعض المسارات الأخرى فلا تتطابق دلالياً بالكامل؛ مثال `/services/تنظيف-واجهات-مباني-بالرياض` مقابل «تنظيف واجهات زجاج بالرياض». لا يجوز اعتبار هذه الحالات متطابقة لمجرد تشابه كلمة عامة.
- جُرّبت مطابقة استكشافية مبسطة بالتجزئة الصوتية، لكنها لم تكن دقيقة بما يكفي لتُعتمد: تعثر في بعض أشكال النقل الصوتي العربية واللاتينية ولم يميز دائماً بين التطابق الصوتي والتقارب الدلالي. لم تُحفظ هذه التجربة في الكود، ولم تُغيّر درجة أي صفحة.

### القرار التنفيذي

- لم يتغير أي رابط أو سجل في قاعدة البيانات، ولم يُرسل أي طلب إلى مزود ذكاء اصطناعي في هذه المتابعة.
- لا يُعالج التحذير بتوسيع المطابقة إلى «أي كلمة مشتركة» أو بتخفيض وزن الفحص؛ فهذا قد يمنح مسارات غير ذات صلة درجة نجاح مصطنعة.
- يستمر العمل بمطابقة محافظة وقابلة للاختبار: قبول التطابق العربي الحرفي والتطابق الصوتي اللاتيني المثبت، واستخدام مرادفات المسارات الثابتة فقط عندما يكون معناها واضحاً ومحدداً. تبقى الحالات غير المثبتة تحذيرات حتى تُحاذى عبارة التركيز مع نية الصفحة أو تُراجع حالة تغيير الرابط منفردة.
- لا يُغيّر أي URL ناجح، ولا يُعدَّل URL فاشل لمجرد هذا التحذير. إذا تعذر إثبات المطابقة الطبيعية وظل الوصول إلى 100/100 متوقفاً على المسار، فالتغيير يتطلب مراجعة منفصلة للصفحة نفسها وتحويل 301 وتحديث الروابط الداخلية وcanonical وsitemap.
- يجب أن تستخدم بوابة البناء وتدقيق لوحة الإدارة قواعد المطابقة نفسها. تُضاف اختبارات للحالات الصوتية المقبولة والحالات المتقاربة التي يجب أن تبقى تحذيراً قبل تغيير نتائج التقرير.

### نتائج تنفيذ المطابقة وإعادة التدقيق — 19 أكتوبر 2026

- أُضيفت قاعدة مطابقة مشتركة للمحلل: التطابق العربي الحرفي أولاً، ثم تهجئة لاتينية صوتية على مستوى الكلمات، مع مرادفات محصورة للمناطق والاتجاهات والصفحات الثابتة المعروفة. في الصفحات غير الثابتة يجب أن تطابق كل الكلمات الجوهرية في عبارة التركيز؛ لا يكفي الاشتراك في كلمة عامة.
