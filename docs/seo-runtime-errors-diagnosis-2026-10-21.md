# تشخيص أخطاء Sitemap وتوليد SEO — سجل التحليل وخارطة الاستكمال

**الحالة:** اكتمل تحليل المصدر والقراءة الحية ضمن الأدلة المتاحة؛ لم تُعدّل الشيفرة أو قاعدة البيانات أو إعدادات الإنتاج.
**نطاق هذه الوثيقة:** مشكلة رابط Sitemap الذي يعرض `__CLEANFLOW_SITE_ORIGIN__`، ورسالة فحص Sitemap، ورفض HTTP 422 لمسارات `generate-blog-basics` و`generate-blog-seo` و`generate-page-seo`.
**قاعدة الاستكمال:** أضف الأدلة والاستنتاجات والخطوة التالية هنا أثناء العمل. لا تعِد مسح المشروع كاملًا. لا تنفّذ إصلاحًا قبل اكتمال تتبع نسختي Node وPHP ومصادر الواجهة والنشر، ومراجعة أثر التعديل على المسارات المشتركة.

**قاعدة النشر التي أكدها المستخدم أثناء هذا التحليل:** PHP على Hostinger هو الهدف الأساسي والافتراضي. المقصود بطلب «حزمة Hostinger» هو PHP، ولا يُختار Node إلا إذا طُلب بالاسم. يجب مع ذلك إبقاء Node وPHP متكافئين في السلوك والواجهات حيثما يدعم التنفيذان الوظيفة.

## أدلة المستخدم

1. عينة XML المعروضة تحتوي على `__CLEANFLOW_SITE_ORIGIN__` في `<loc>` و`xhtml:link` وروابط الصور بدل عنوان HTTPS فعلي.
2. واجهة التدقيق تعرض: «الملف المستلم ليس خريطة موقع XML صالحة»، ولا يظهر سبب إضافي في Console حسب المستخدم.
3. طلب الإنتاج `POST /api/admin/ai/generate-blog-basics` يرجع 422، ونص الخادم يقول إن عبارة التركيز غير موجودة في الكلمات المقاسة، وإن العنوان يجب أن يحقق طول Rank Math ويتضمن العبارة حرفيًا.
4. طلب `POST /api/admin/ai/generate-page-seo` يرجع 422 أيضًا. لم يصلنا نص استجابة هذا الطلب كاملًا ولا الـpayload؛ لا يجوز اعتبار سببه مطابقًا لخطأ المدونة دون قراءة المسار.
5. الـConsole يثبت وصول الطلبات إلى `aiservx.com`. فحص ترويسات HTTP الحية أكد أن هذا النطاق يعمل على Hostinger/PHP، وليس Node.

## مواضع التنفيذ التي تم ربطها

- نص خطأ Sitemap موجود في `artifacts/sabaik-almasa/src/lib/seo-audit.ts` قرب السطر 954. الفحص الظاهر يبدأ بالبحث عن وسم `<urlset>`؛ هذا ليس محلل XML كاملًا ولا يتحقق بمفرده من أن `<loc>` روابط مطلقة أو من عدم بقاء token.
- مسارا التوليد موجودان في واجهة React وخادم Node (`artifacts/api-server/src/routes/aiSeo.ts`) وتنفيذ PHP (`scripts/api-index.php`). الترويسات الحية ورسالة 422 يثبتان أن Hostinger/PHP هو التنفيذ المعني هنا؛ Node داخل المقارنة لأجل التكافؤ فقط.
- بوابة العبارة/العنوان ورسالة الكلمة المقاسة موجودة في PHP، كما أن حزمة Hostinger تنسخ الـAPI ومساعدات السياسة وتوجه `/api/*` إلى `api/index.php`. لم يظهر دليل على route مفقود أو ملف API في موضع خاطئ.
- يوجد token للأصل في مخرجات/أصول الموقع ومسارات استبدال في بناء Vite وPHP وNode؛ وجود استبدال متعدد المسارات يجعل التمييز بين XML ساكن، XML مولّد وقت الطلب، وملف بناء/أرشيف غير معالج خطوة لازمة.

## نتيجة قراءة حيّة وتتبّع أولي — 2026-10-21

- ترويسات `aiservx.com/sitemap.xml` و`aiservx.com/api/sitemap/generate` الحية تعرض `X-Powered-By: PHP/8.3.35` و`platform: hostinger`. هذا يثبت أن الدومين الذي ظهر في Console يخدم PHP على Hostinger؛ لا أتعامل مع Node كبيئة الخطأ.
- بيانات نشر Replit لا تُظهر نشرًا لهذا الـRepl؛ لذلك سجلات Replit لا تمثل خادم Hostinger الخارجي، ولم أستخدمها لإسناد أخطاء الإنتاج.
- طلبات GET عامة للقراءة فقط إلى العناوين التي ظهرت في السياق أعادت:
  - `https://aiservx.com/sitemap.xml`: HTTP 200 و`application/xml`، جذر XML من نوع `<sitemapindex>` يشير إلى 3 ملفات فرعية على النطاق نفسه.
  - `https://aiservx.com/sitemap1.xml` و`/sitemap2.xml` و`/sitemap3.xml`: HTTP 200، وكل ملف `<urlset>` ويحوي `<loc>` مطلقًا على `aiservx.com`، دون ظهور token في المتن الحالي.
  - `https://alsahmm.com/sitemap.xml`: HTTP 200 و`application/xml`، `<urlset>` وروابط مطلقة على `alsahmm.com`، دون ظهور token في المتن الحالي.
  - `https://aiservx.com/api/sitemap.xml`: HTTP 404؛ هذا ليس مسار ملف الخريطة في التطبيق. واجهة الفحص تطلب `/sitemap.xml` من أصل الصفحة، أما `/api/sitemap/generate` فهو API معاينة يعيد JSON يحتوي XML وليس ملف XML نفسه.
- **سبب مثبت لرسالة فحص Sitemap على أصل `aiservx.com`:** الجذر الحي هو فهرس sitemap من نوع `<sitemapindex>`، اجتاز تحليل XML ويشير إلى 3 ملفات فرعية HTTPS على الأصل نفسه. `runSeoSiteAudit` يرفضه قبل استدعاء `loadSitemapPageTargets` بسبب شرط مبكر لا يقبل إلا `<urlset>`, رغم أن الدالة التالية تدعم `<sitemapindex>` وتحمل ملفاتها. لذلك الرسالة تشخيص خاطئ لنوع خريطة صالح، وليست إثباتًا أن XML غير سليم.
- **لم يُعَد إنتاج ظهور الـtoken على الدومين الحي الحالي.** في بناء PHP، ينشئ `build-hostinger.mjs` الخريطة ويفحصها، ثم يحول الأصول في `build_php` إلى `__CLEANFLOW_SITE_ORIGIN__` في خطوة لاحقة. الأرشيف يعتمد لذلك على قاعدة `.htaccess` التي تعيد `/sitemap.xml` وملفات التقسيم إلى `site-response.php`؛ هذا المسار يستبدل token بأصل طلب PHP. قاعدة rewrite موجودة قبل تجاوز الملفات الموجودة، لذا تعمل في الحزمة المطابقة للمصدر. لكن تعليق البناء يقول إن الملف الساكن صالح حتى مع تعطّل rewrite، وهذا غير صحيح بعد تحويل الأصل إلى token. إذا كانت قواعد الموقع المنشور قديمة/مفقودة أو كانت العينة من مسار/نطاق آخر، يمكن أن يظهر token. رابط العينة الكامل ما زال مطلوبًا لتحديد حالة الإنتاج بدقة.
- **دليل تعيين 422 إلى PHP:** نص 422 للمدونة يطابق حرفيًا فرع PHP في `scripts/api-index.php`. الدومين الحي نفسه يعلن PHP/Hostinger، والـroute موجود في PHP ومضمّن في حزمة البناء. لا يوجد دليل على route مفقود أو ملف API في موضع خاطئ؛ 422 هو رد تحقق من المسودة بعد وصولها إلى المعالج، لا 404 ولا خطأ مزود.
- في PHP، عبارة التركيز تُقبل إذا طابقت كلمة مقاسة **أو tag مولدًا**، بينما نص الفشل يقول إنها يجب أن تكون من الكلمات المقاسة فقط. كما أن العنوان لا يُصلح إلا بعد قبول العبارة. إذا اختار النموذج عبارة غير مسموحة، يتخطى إصلاح العنوان وتظهر الرسالتان معًا. هذا يفسر نمط الرفض دون أن يعني أن خدمة AI تعطلت؛ ولا نعرف من الرسالة قيمة العبارة أو طول العنوان اللذين ولّدا الفشل.
- قائمة الكلمات ليست حجم بحث أو بيانات Google: PHP يحسب قوة داخلية من مرات الظهور وتوزع العبارة على الصفحات والمقالات وملكية الصفحات لها. هذه إشارة لتغطية محتوى الموقع، مفيدة للمراجعة الداخلية، لكنها لا تقيس الطلب أو الانطباعات أو ترتيب Google.
- سياسة العنوان تضبط `minimum=30` و`targetMinimum=50` و`maximum=60`. المحلل وبوابة 422 يقبلان 30–60؛ 50–60 توجيه للتوليد وليس حدًا حاجبًا فعليًا. كما أن فحص العبارة يطبّع اختلافات الحروف/التشكيل والمسافات، لذلك «حرفيًا» في الرسالة ليست وصفًا دقيقًا للمقارنة البرمجية.
- مسار `generate-page-seo` منفصل: كلمة التركيز من `keyword` أو العنوان، ثم تُفحص العناوين والوصف ووجود العبارة وكونها أول `seoKeywords` وslug وCanonical بعد محاولتين. في PHP يُصلح عنوان SEO؛ Node لا يطبق هذا الإصلاح نفسه. واجهة الصفحة تقرأ JSON وتعرض `error` في toast؛ Console يثبت 422 فقط. من دون Response JSON لا يمكن تسمية شرط الصفحة الذي فشل بدقة.
- يوجد انجراف سلوكي PHP/Node يجب علاجه معًا لاحقًا: توليد أساسيات المقال في Node يقبل قائمة الكلمات المقاسة فقط ولا يصلح العنوان؛ PHP يقبل القائمة أو tags ويصلح العنوان عند صلاحية العبارة. وفي توليد بيانات الصفحة يصلح PHP العنوان بينما لا يفعل Node. حاليًا PHP هو هدف الإصلاح، ويُفحص Node للتكافؤ لا كبديل للنشر.
- واجهة `SeoSiteAudit.startAudit` تمسك الاستثناء وتعرضه في حالة React دون `console.error`؛ غياب الخطأ في Console متوقع من مسار العرض الحالي ولا يعني أن المتصفح لم يواجه شرط الفشل.
- الاختبارات المرتبطة نجحت: `php scripts/test-seo-title-repair.php`، واختبارات sitemap الحالية **7/7**. هذه تغطي إصلاح العنوان وتوليد/تقسيم sitemap، لكنها لا تغطي شرط فحص الواجهة الذي يرفض sitemapindex ولا مساري توليد AI.

## فرضيات الفحص الأولية (أرشيفية؛ الخلاصة النهائية أدناه هي المرجع)

1. ظهور token قد يعني أن خريطة الموقع أو نسخة عامة من مخرجات البناء تُقدَّم كملف ثابت قبل مرورها على مستبدل الأصل في PHP/Node، أو أن مسار الاستبدال لا يشمل `sitemap.xml` أو يقرأ أصلًا غير مضبوط.
2. رسالة “XML غير صالح” قد تكون ناتجة من استجابة أخرى غير عينة XML (مثل HTML أو redirect أو خطأ صلاحيات)، أو من طلب إلى URL مختلف. النص المعروض وحده لا يثبت ذلك. إذا كان المتن الذي قرأه المدقق هو XML المعروض حرفيًا، فشرط `<urlset>` البسيط المكتشف يجب أن يمر؛ يجب تتبع URL الطلب والمتن والحالة في الكود بدل تخمين أن token يكسر بناء XML.
3. خطأ 422 في التوليد يبدو رفضًا متعمدًا من بوابة الجودة. السبب الجذري المحتمل قد يكون اختلافًا بين عبارة التركيز المختارة وقائمة الكلمات المقاسة، أو عدم إعادة كتابة العنوان بعد اختيار العبارة، أو اختلاف المدخلات/السياسة بين واجهة Node وPHP. يلزم فحص ترتيب الاختيار وإعادة المحاولة والتطبيع ومدخلات Rank Math في التنفيذين قبل التوصية.
4. خطأ `generate-page-seo` يحتاج استجابة JSON كاملة ومدخلات الطلب أو قراءة قواعد المسار؛ لا يوجد دليل كافٍ أنه نفس خطأ عنوان/عبارة المدونة.

## قائمة تحقق التحليل الأولية (اكتملت في 2026-10-21؛ خارطة التنفيذ النهائية أدناه)

### أ. إثبات مصدر Sitemap واستجابة التدقيق

- تتبع `startAudit` من واجهة `SeoSiteAudit` إلى عنوان جلب Sitemap، ثم نوع الاستجابة والـstatus والـredirect وقراءة النص والشرط الذي يرمي الرسالة.
- تتبع `sitemap.xml` من ملف/مولد البناء إلى قواعد rewrite وPHP runtime وNode route، وتحديد precedence بين ملف ثابت ومسار ديناميكي.
- فحص مسار تعويض `__CLEANFLOW_SITE_ORIGIN__` في archive/PHP/Node، بما في ذلك الروبوتات وXML والصور؛ ومقارنة مع إعداد الأصل الحالي دون كشف أسرار.
- الحصول على استجابة GET عامة فعلية من النطاق الإنتاجي الذي يحدده المستخدم/معلومات النشر، مع `status`, `Content-Type`, redirects، أول `<loc>`، وطلب كل عنوان ممثل. لا ترسل POST إنتاجي إداري ولا تحاول تجاوز المصادقة.
- التحقق من أن المدقق يتحقق من XML فعليًا، ومن أن تشخيصه يفرق بين HTTP/redirect/HTML/XML غير صالح/روابط نسبية أو token متبقٍ. هذا تشخيص تصميم وليس قرار تعديل.

### ب. إثبات تنفيذ مسارات التوليد وسبب 422

- تتبع مساري `/api/admin/ai/generate-blog-basics` و`/api/admin/ai/generate-page-seo` من جسم الطلب في `Blog.tsx` و`SeoPages.tsx`، مرورًا بتوجيه API/auth والـhandler إلى تكوين الاستجابة.
- مقارنة Node وPHP: من يختار focus phrase، كيف يختار/يعيد ترتيب الكلمات المقاسة، كيف يُولّد العنوان، سياسة عدد الأحرف، وكيف تُحسب الإخفاقات قبل إرجاع 422.
- التحقق من علاقة `focusKeyword` بقائمة الكلمات بعد التطبيع العربي/الإنجليزي، ومن ترتيب إعادة المحاولات: هل يعاد توليد المخرجات أم يعاد فحص نفس المسودة؟ لا تضعف بوابة Rank Math لإخفاء الرفض.
- فحص نص الاستجابة الكامل لـ422 في مساري الإنتاج عند توفر صلاحية آمنة، أو اعتماد handler واختبارات/بيانات طلب معقمة. لا تطبع بيانات جلسة أو رموز مصادقة.
- تحليل ارتباط الاعتماديات والمساعدات المشتركة بين endpoint المدونة وصفحات SEO، ومسار PHP الموازي، ثم تدوين اختبارات تكافؤ لازمة قبل أي تعديل.

### ج. خريطة اعتماد وتقييم المخاطر قبل الإصلاح

- تحديد الملفات المشتركة التي تعتمد عليها هذه المسارات، وسيناريوهات احتمال كسر Sitemap/robots/canonicals والبوابة التحريرية عند التغيير.
- فصل تغييرات إنتاج الواجهة عن API وعن PHP/حزمة Hostinger؛ أي مسار لا يتضمنه الإصلاح يجب التصريح بأنه خارج النطاق.
- صياغة إصلاحات صغيرة مرتبة حسب السبب المثبت، لكل منها قبول قابل للقياس واختبارات Node/PHP/واجهة وحزمة الإنتاج.
- لا تغيير URLs أو سياسة القياس أو شروط القبول بلا قرار صريح ومدعوم بالدليل؛ لا تنشر ولا تعدل بيانات الإنتاج أثناء التشخيص.

## خارطة التنفيذ الآمنة بعد اكتمال التحليل

هذه خطة العمل التالية، وليست تصريحًا بتغيير الموقع الآن. التنفيذ يبدأ على PHP/Hostinger، ثم يثبت تكافؤ Node. لا تُضعف شروط الجودة ولا تغيّر canonical أو URL مستقرًا لإسكات الخطأ.

### 1A. أصلح رفض sitemapindex الصالح — مكتملة (النطاق الموافق عليه)

- أُزيل شرط الواجهة الذي كان يقبل `<urlset>` فقط؛ `runSeoSiteAudit` يمرر الجذر الآن إلى محلل يدعم `<urlset>` و`<sitemapindex>`.
- حُفظت حماية same-origin؛ الاختبار يثبت أن shard على النطاق نفسه يُجلب وأن shard خارجي لا يُتبع.
- اجتاز `test:seo-audit-urls`، وTypeScript، وبناء Vite، وإعادة تشغيل workflow ومعاينة الصفحة العامة.
- لم يتغير مولد Sitemap أو PHP/Node أو بيانات الإنتاج، ولم يتم النشر.

### 1B. استكمال تشخيص استجابة Sitemap والتحقق الصارم — مكتملة محليًا

- افحص حالة HTTP ونوع المحتوى ووجهة التحويل، وافصل تشخيص HTML/404 عن XML غير الصالح والفهرس الذي لا يحتوي ملفات صالحة.
- تحقّق من عدم بقاء `__CLEANFLOW_SITE_ORIGIN__` في المستند أو روابطه قبل بدء تدقيق الصفحات.
- اكتمل التحقق من HTTP وحالة الاستجابة ونوع المحتوى ووجهة التحويل، مع فصل حالات HTML/404/XML غير الصالح.
- يُرفض token غير المستبدل في نص الخريطة أو روابطها قبل بدء تدقيق الصفحات.
- أضيفت اختبارات للأنواع غير الصالحة، و404، وMIME HTML، والتحويل إلى أصل خارجي، والروابط النسبية، والفهرس الفارغ أو غير الآمن.
- اجتاز `test:seo-audit-urls` بعد هذه الإضافات. لم تُسجل بيانات دخول أو أسرار، ولم يتغير مولد Sitemap أو بيانات الإنتاج.

**سجل التنفيذ والنتائج:**

- حُذف الرفض المسبق داخل `runSeoSiteAudit`؛ أصبح المحلل المشترك يقرر بين `urlset` و`sitemapindex`.
